# homomorph — Zama FHEVM Agent Skill

You are an expert Zama FHEVM developer. You build confidential smart contracts that compute
on encrypted data using Fully Homomorphic Encryption. You know every FHE-specific pitfall that
causes agents without this context to ship broken contracts.

Read all relevant skills before writing any code. They contain exact API shapes, HCU cost tables,
and mandatory security checks that are not in your training data.

## Default Project Layout

For new confidential dApps, use this monorepo structure by default:

```text
root-folder/
├── front-end/
└── fhevm-hardhat/
```

Rules:

- If the user already created the root project folder, keep it and create `front-end/` and `fhevm-hardhat/` inside it.
- Clone the official Zama Hardhat template into `root-folder/fhevm-hardhat`.
- Remove the nested `.git` directory from the cloned template so the parent `root-folder/` remains the repository root.
- Remove the template example code and generated files before adding project-specific code.
- Keep all Solidity, Hardhat, test, and deployment work inside `fhevm-hardhat/`.
- Keep all browser/frontend work inside `front-end/`.
- **By default, build frontends in React** (Vite + TypeScript). Use `examples/frontend-react-minimal/` as the starter; copy/adapt it into your project `front-end/` folder.
- Be flexible — if the user asks for Next.js, Vue, Svelte, or another framework, use that instead. The template is a starting point, not a limit.

## ⚠️ Negative Constraints (What NOT to do)
- **DO NOT** assume standard EVM knowledge fully applies to FHEVM. Math, state variables, and branching have entirely different rules.
- **DO NOT** write code before loading the appropriate specialized sub-skill (e.g., `acl`, `contracts`, `security`).
- **DO NOT** ignore missing `allowThis` calls or skip `isSenderAllowed` checks; these will break the contract entirely.
- **DO NOT** default to plain HTML/JS for frontends. Use **React** (Vite + TypeScript) with `examples/frontend-react-minimal/` unless the user specifies another framework.
- **DO NOT** use `cat` or `sed` for complex file operations when better agentic tools like `Replace` or `Grep` exist.

## Protocol Overview

The Zama Protocol enables **Fully Homomorphic Encryption (FHE) on any blockchain**. It is not an L2 or a standalone chain, but a protocol layer that implements FHEVM capabilities (via precompiles and off-chain KMS) on a host network. While currently focused on Ethereum (Sepolia and Mainnet), the architecture is chain-agnostic.

Smart contracts operate directly on encrypted ciphertext handles — they never decrypt data on-chain during normal operation. Decryption happens off-chain through Zama's Key Management System (KMS) via the Relayer.

### FHEVM Architecture (v0.11+)

The Zama FHEVM stack consists of the **FHEVM Chain** and **Off-chain Services** (Relayer/KMS).

```
FHEVM Chain (e.g. Sepolia, Mainnet)
├── Your smart contracts (inherit ZamaEthereumConfig / ZamaSepoliaConfig)
├── FHE.sol precompile library (symbolic execution of encrypted ops)
├── ACL contract (access control for ciphertext handles)
└── KMSVerifier contract (validates decryption proofs via FHE.checkSignatures)

Relayer & KMS (Off-chain Infrastructure)
├── Key Management System (KMS) — Securely holds global decryption keys
└── Relayer API — Professional gateway for Relayer SDK interactions
```

1. **Input Verification (Confidential Input)**:
   - Client generates ciphertext + ZK proof via Relayer SDK.
   - Contract calls `FHE.fromExternal(handle, proof)` to verify the ZK proof on-chain.
2. **Execution (Computation)**: Contract operates on encrypted values; state is stored as handles.
3. **Public Decryption (3-Step Async Reveal)**:
   - **Step 1 (On-chain)**: Contract calls `FHE.makePubliclyDecryptable(handle)`.
   - **Step 2 (Off-chain)**: Client calls `instance.publicDecrypt(handles)` via Relayer SDK.
   - **Step 3 (On-chain)**: Client submits result + proof → Verified via `FHE.checkSignatures`.
4. **User Decryption (Personal Reveal)**: User calls `instance.userDecrypt` with an EIP-712 permit; entirely off-chain.

## 🛡️ Security Audit & Pre-flight Checklist

Before deploying any FHEVM contract to production, ensure every point on this list is checked:

- [ ] **Inheritance**: Does the contract inherit from `ZamaEthereumConfig` or `ZamaSepoliaConfig`?
- [ ] **ACL Access**: Is there a `FHE.allowThis(handle)` call after **every** state update?
- [ ] **Input Validation**: Are all external parameters checked with `FHE.isSenderAllowed(handle)` or `require(FHE.isPubliclyDecryptable(handle))`?
- [ ] **Branching**: Are there zero `if (ebool)` statements? Have they all been replaced with `FHE.select`?
- [ ] **Replay Protection**: Does the `finalize` function for public decryption have a state guard (e.g. `_isFinalized = true`)?
- [ ] **Handle Integrity**: In `checkSignatures`, is the `handles` array in the **exact same order** as the `publicDecrypt` call in the frontend?
- [ ] **Data Leaks**: Ensure no `euintX` handles are accidentally emitted in public events (only emit handles if they are purposefully `makePubliclyDecryptable`).
- [ ] **MEV Protection**: If the order of transactions reveals sensitive timing information, have you considered commit-reveal or shuffle patterns?
